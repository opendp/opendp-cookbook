Streaming Large Files with Polars#

OpenDP uses Polars to compute its queries. By default, Polars loads all the columns a query needs into memory before it computes anything. Polars also has a streaming engine, which reads the data in batches, so you can query a file that is larger than memory.

Use streaming when your file is close to the size of your machine’s memory, or larger. If the data fits easily, the default engine is fine.

Most DP queries can use the streaming engine: counts, sums, means, grouping, and most transformations of the data. In OpenDP 0.16, quantile queries can’t. This recipe shows how to stream a DP query, how much memory it saves, and what to look out for.

Making a large test file#

We make up a CSV file with 3 million rows. That fits in memory easily, but it is big enough to show the difference. We write it in chunks, so that making the file doesn’t use much memory itself.

[1]:

import re
import resource
import sys
import tempfile
import time
from pathlib import Path

import numpy as np
import opendp.prelude as dp
import polars as pl

dp.enable_features("contrib")

rng = np.random.default_rng(42)
states = ["CA", "NY", "TX", "WA"]
n_rows = 3_000_000
chunk_size = 500_000

temp_dir = tempfile.TemporaryDirectory()
csv_path = Path(temp_dir.name) / "people.csv"
with csv_path.open("w") as csv_file:
    for start in range(0, n_rows, chunk_size):
        pl.DataFrame(
            {
                "state": rng.choice(states, chunk_size),
                "age": rng.integers(18, 90, chunk_size),
                "income": rng.integers(0, 200_000, chunk_size),
            }
        ).write_csv(csv_file, include_header=start == 0)

print(f"{csv_path.stat().st_size / 2**20:.0f} MB on disk")

36 MB on disk

pl.scan_csv doesn’t read the file. It returns a LazyFrame, which is a plan to read the file later. (For Parquet files, use pl.scan_parquet.) OpenDP accepts a LazyFrame as its data, so nothing is loaded yet.

The margins describe what we know about the data without looking at it. max_length says the table has at most 3 million rows, in total and in each state. invariant="keys" says the list of states is public, so it doesn’t need to be protected.

We split the budget evenly over three releases: two that compare the engines, and one quantile at the end.

[2]:

context = dp.Context.compositor(
    data=pl.scan_csv(csv_path),
    privacy_unit=dp.unit_of(contributions=1),
    privacy_loss=dp.loss_of(epsilon=1.0),
    split_evenly_over=3,
    margins=[
        dp.polars.Margin(by=[], max_length=n_rows),
        dp.polars.Margin(by=["state"], invariant="keys", max_length=n_rows),
    ],
)

Streaming a query#

In OpenDP 0.16, release() returns a OnceFrame, and OnceFrame.collect() always uses the default in-memory engine. To pick the engine yourself, take the plan out of the OnceFrame with .lazy(), then call collect(engine="streaming") on the plan.

.lazy() needs the "honest-but-curious" feature, because it removes protections, and you have to keep the privacy promises yourself:

  • Collect the plan only once. Each collect is a new noisy release, and together they leak more than the budget you set.

  • Don’t keep the OnceFrame after calling .lazy(). It can still be collected, and that would be another release that the budget doesn’t count.

  • Don’t look at the order of the output rows, because the order can reveal information about the data. Don’t add steps to the plan that depend on row order (like head or with_row_index), and shuffle the output once you have collected it, as the `lazy() docs <https://docs.opendp.org/en/stable/api/python/opendp.extras.polars.html#opendp.extras.polars.OnceFrame.lazy>`__ say.

Once enabled, the feature stays on for the rest of the Python session.

Each release below is a count and a mean income for each state. signed=True keeps negative noisy counts (see the signed counts recipe in this section). fill_null(0) is needed because OpenDP can’t know that the file has no missing values.

[3]:

dp.enable_features("honest-but-curious")

[4]:

def release_plan():
    """Releases a count and a mean income for each state, and returns only the plan, to collect once."""
    query = (
        context.query()
        .group_by("state")
        .agg(
            dp.len(signed=True),
            pl.col("income").fill_null(0).dp.mean((0, 200_000)),
        )
    )
    return query.release().lazy()

We release the same statistics twice only to compare the two engines. In a real analysis you would release them once.

[5]:

streaming_plan = release_plan()
in_memory_plan = release_plan()

Checking that the plan streams#

Before you collect, you can check which parts of the plan the streaming engine will run. show_graph with plan_stage="physical" describes the steps without running them. Here we pick out the name of each step. A step called in-memory-map would mean that Polars falls back to the in-memory engine for that part.

[6]:

def physical_steps(plan):
    """Returns the names of the steps the streaming engine would run for this plan."""
    graph = plan.show_graph(engine="streaming", plan_stage="physical", raw_output=True)
    return sorted(set(re.findall(r'\[label="([^"\\]+)', graph)))


physical_steps(streaming_plan)

[6]:

['group-by', 'multi-scan[csv]', 'select']

Every step here runs in the streaming engine. When a step isn’t supported, Polars falls back quietly, without a warning. The query still gives the right answer, but it may use more memory than you expect.

How much memory it saves#

To see how much memory each engine takes, we look at the peak memory of the whole Python process (its “resident set size”). The peak never goes down, so we collect with the streaming engine first, then with the in-memory engine, and print the peak before and after each one. The resource module only exists on Linux and macOS.

[7]:

def peak_mb():
    """Returns the peak memory of this process so far, in megabytes."""
    peak = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    # Linux reports kilobytes, and macOS reports bytes.
    return peak / 2**20 if sys.platform == "darwin" else peak / 2**10


def timed_collect(plan, engine):
    """Collects the plan once with the given engine, prints time and peak memory, and shuffles the rows."""
    before = peak_mb()
    start = time.perf_counter()
    released = plan.collect(engine=engine)
    seconds = time.perf_counter() - start
    print(
        f"{engine:>9}: {seconds:.2f} s, peak memory {before:.0f} MB -> {peak_mb():.0f} MB"
    )
    return released.sample(fraction=1, shuffle=True)


streamed = timed_collect(streaming_plan, "streaming")
in_memory = timed_collect(in_memory_plan, "in-memory")

streaming: 0.11 s, peak memory 265 MB -> 332 MB
in-memory: 0.18 s, peak memory 332 MB -> 537 MB

The in-memory engine starts from the streaming peak, so the difference between its two numbers is the least it needed beyond what streaming used. When we ran this, streaming raised the peak by about 90 MB, and the in-memory engine raised it by over 200 MB more. Your numbers will be different, and streaming may also be faster.

The gap grows with the size of the file: the in-memory engine needs room for every value it reads, while the streaming engine only needs room for a few batches at a time. In separate runs with 1, 3 and 10 million rows, each engine in a fresh process, the in-memory engine needed 2.5 to 3.2 times as much extra memory as the streaming engine.

What can’t stream#

In OpenDP 0.16, .lazy() fails on a quantile query, because OpenDP can’t hand a quantile’s plan over to Polars in Python yet. The release has already spent its budget by then, but the OnceFrame is not used up, so you can still collect it with the in-memory engine.

[9]:

quantile_query = context.query().select(
    pl.col("age").fill_null(0).dp.quantile(0.5, candidates=list(range(18, 91)))
)
released_quantile = quantile_query.release()
try:
    released_quantile.lazy()
except dp.OpenDPException as error:
    print("lazy() failed:", error.message.split("error: ")[-1].split('"')[0])

released_quantile.collect()

lazy() failed: serialization not supported for this 'opaque' function

Native support for the streaming engine in OnceFrame.collect() is tracked in opendp/opendp#3138. Once that lands, you won’t need .lazy() or the "honest-but-curious" feature.

temp_dir.cleanup()

Takeaways#

  • Stream when your data is close to the size of your memory, or larger.

  • Give OpenDP a LazyFrame from pl.scan_csv or pl.scan_parquet, so the file isn’t loaded up front.

  • To stream, use release().lazy().collect(engine="streaming"). Collect only once, drop the OnceFrame, and shuffle the output.

  • Check the plan with show_graph(engine="streaming", plan_stage="physical") to see whether anything falls back to memory.

  • Counts, sums, means and grouping stream well. Here the in-memory engine needed 2.5 to 3.2 times as much extra memory.

  • Quantiles don’t stream in OpenDP 0.16, but you can still collect them in memory.
